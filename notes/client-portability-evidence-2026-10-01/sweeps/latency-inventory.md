## 0. Conventions and caveats

- Paths are repo-root-relative: `go/...` is `/Users/hugh/kek/lip/go/...`, `notes/...` is `/Users/hugh/kek/lip/notes/...`. `file:N` is a 1-based line, `file:N-M` a range. Stage directory names are written in full so every citation resolves mechanically.
- `†` marks code outside the file list in the prompt. The prompt asks for the F1 deadline, ping/pong, order ack and fill observation, which live in `wsx/session.go`, `wsx/supervisor.go`, `rest/*`, `cfg`, `lifecycle`, `core` and `cmd/*`; I located them by grep and read them read-only.
- "stated" = a number written in a note. "derived" = my recomputation from raw rows (method given). "design" = a configured or spec value, not a measurement.
- Percentiles are nearest-rank on the sorted values (index `round(p*(n-1))`).
- `*.db` access: only `sqlite3 -readonly 'file:PATH?immutable=1&mode=ro'`. Immutable mode ignores `-wal`, so rows committed after the last checkpoint are invisible. The r2 EFRE and r2 MCI stores carry a 4.1 MB WAL each and are partial (EFRE: 2 of 4 fills, 5 of at least 7 orders; MCI r2: 2 of 3 fills, both orders). One survey pass counted rows in all 16 `*.db` files (one is a 32-byte non-database fixture) to find which hold orders and fills; the five stores with orders were then read for `owned_order`, `our_fill` and `balance_poll`. DB-derived rows cite the table, not a line.
- Not used as evidence: `notes/client-portability-evidence-2026-10-01/` (the parent's own in-progress review) and compiled binaries.
- Recomputation was done in memory with `python3` heredocs; nothing else was written.

## 4. Task C: gaps a low-latency trading client would want measured

1. Per-request REST timing and phase breakdown. The production Doer reads no clock around `d.Client.Do` (`go/harness/rest/client.go:329-386`), uses no `httptrace` (DNS, connect, TLS, first byte), and the qualification recorder keeps counts with no status or duration (`go/harness/qual/recorder.go:411-438`). Only the cancel sweep trace (wall, stderr) and the read-only `cmd/accountcheck` tool time requests.
2. Order submit-to-ack as a first-class metric. Only `bound_ms - reserved_ms` exists; it folds in the SQLite permit wait and a slow first order, and also covers adoption binds. The create and cancel responses carry `ts_ms` (`go/harness/rest/write.go:422-423`, `go/harness/rest/cancel.go:174`) that is ignored (`ack` struct `go/harness/rest/write.go:414-418`), so exchange-side processing time and clock offset are lost; there is no cancel-ack latency either.
3. Fill observation quality. Fills are found only by the 5 s REST poll (`go/harness/cfg/params.go:136`; the socket subscribes `orderbook_delta` and `trade` only, `go/harness/wsx/wire.go:31-45`; whether the exchange offers a private fill feed is not established in `notes/`). `exchange_ts_ms` is whole seconds (`go/harness/rest/read.go:644`, `go/harness/rest/read.go:652-668`) and `first_seen_ms` is stamped after the full three-walk cycle (`go/cmd/harness/run.go:1868`), so the store cannot separate poll wait, round trip and exchange visibility lag, and over-states lag by 0.37-0.80 s.
4. Websocket delivery lag and cadence. Every snapshot, delta and trade frame carries an exchange `ts_ms` (`go/core/rig.go:235`, `go/core/rig.go:242`, `go/core/rig.go:251`) that is never compared with the local receive time; the receive stamp is taken after a JSON decode and a channel hand-off (`go/harness/wsx/session.go:223`, `go/harness/wsx/session.go:231`); no per-frame arrival series, queue depth or inter-frame-gap histogram is kept (only the 60 s `BOOK_QUIET`, `go/harness/wsx/gate.go:1117`).
5. Ping/pong RTT. `Socket.Ping` returns only an error (`go/harness/wsx/transport.go:42`, `go/harness/wsx/transport.go:195`); the pong is pass/fail against 5 s, so there is no RTT series and no early warning below the ladder.
6. Connection setup and cold-start cost. DNS lookup (`go/harness/netx/dns.go:144`), TCP connect (`go/harness/netx/dns.go:177-192`), TLS, websocket upgrade and subscribe-to-first-snapshot are untimed, bounded only by timeouts (`go/harness/wsx/supervisor.go:307`, `go/cmd/harness/runtime.go:229-230`, `go/cmd/harness/runtime.go:300`). The cold penalty (first GET about 234 ms; first order 430-538 ms) is visible only in tool output, and the reconnect duration is never persisted (only a count and first/last time per event name, `go/harness/qual/recorder.go:196-202`).
7. Clock offset to the exchange. Not measured; B.1 suggests the local wall clock reads tens of ms behind. Signing (`go/harness/rest/client.go:357`), the fills `since` filter (`go/harness/rest/read.go:567-568`) and the HTTP-date `Retry-After` (`go/harness/rest/throttle.go:55-60`) all depend on it. F7 (`go/harness/lifecycle/sleep.go:87-149`) detects wall-vs-monotonic divergence only.
8. Rate-limit telemetry. Individual 429s, `Retry-After` values, token-bucket wait and a per-endpoint request-rate and status histogram are not persisted (`go/harness/rest/throttle.go:16-21` lives in memory; only a SEV2 after 60 s sustained, `go/cmd/harness/dispatch_throttle.go:54-57`; qual HTTP counts have no status), so rate-limit headroom for a faster client cannot be derived from past runs.
9. Disconnect cause. `Event.Cause` (`go/harness/wsx/session.go:88-91`) is dropped by the owner and the `WS_DISCONNECT` row has no cause, so F1 read deadline, pong timeout, close frame and handshake rejection can be told apart only from timing.
10. Internal pipeline latency. Frame-to-decision (read, owner dequeue, evaluate, dispatch), write-queue wait under `write_rate` 5/s and `write_burst` 10 (`go/harness/cfg/params.go:53-54`), the reservation permit wait before dispatch (`go/cmd/harness/dispatch.go:144`, `go/cmd/harness/dispatch.go:156`) and the writer's commit latency (only a 5 s stall bound, `go/harness/hstore/writer.go:132`) are not recorded; the only tail-latency numbers are an offline replay benchmark of `rig.Handle` (`notes/scoreboard.md:24-28`).
