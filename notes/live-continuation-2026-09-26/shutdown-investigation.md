# Shutdown `os.Exit` report: bounded investigation

The readiness report records an exploratory worker package run during concurrent edits that reported a shutdown `os.Exit` panic, but says the complete trace was not preserved. I found no retained log containing that panic in `notes/live-readiness-2026-09-26` or `loop/gates-out`. The older gate log `loop/gates-out/20260926T214110855480Z-a927b615/test-module.log` has a `shutdown.runResults` frame under `TestOwnerF5ReducerSweepResizeRefreshAndRecovery`, but it is a two-minute goroutine dump from a hung test, **not** an `os.Exit` panic. It must not be attributed to the exploratory failure.

The process exit is reachable only from `shutdown.drainLoop` (`go/cmd/harness/shutdown.go:271-310`). `newShutdown` installs the real `os.Exit` at lines 115-120. The drain loop calls it after `observeDrain` authorizes an exit, `stop` succeeds, and qualification evidence finalizes if present. `DrainTracker.Observe` (`go/harness/lifecycle/drain.go:340-350`) authorizes only a valid planned permit plus current known, flat, unrested truth. A signal supplies the planned permit through `shutdown.onSignal`; the normal owner supplies observations through `offerDrain` (`go/cmd/harness/run.go:807-818`). Thus a complete reproduction needs an active drain loop, a committed SIGINT/SIGTERM, then known-flat/unrested observation. An automatic global halt alone does not grant exit authority.

The named F5 test does **not** provide that path: `newGateFailOwner` creates `h.ownerFor()`, whose comment and body (`go/cmd/harness/seam_test.go:1192-1209`) explicitly avoid `serve`; the F5 test (`go/cmd/harness/crosscheck_test.go:251`) starts `runResults` and `dispatchLoop`, but no `drainLoop` and no signal. The single focused command `cd go && go test ./cmd/harness -run '^TestOwnerF5ReducerSweepResizeRefreshAndRecovery$' -count=1 -v` passed on 2026-09-26 (exit 0; test 0.12s; package 0.789s). Retained later module and race gate logs also show this test passing. This does not explain the worker's unretained panic.

There is a real **test-process exposure** in the broader seam harness: `seamHarness.start` (`go/cmd/harness/seam_test.go:1082-1092`) calls `rig.serve(ctx)`, which constructs `newShutdown` with the real `os.Exit`. Its callers normally trigger automatic halts, not a signal permit; the composed signal test instead calls `serveWithShutdown` and replaces `sd.exit` before starting it (`go/cmd/harness/signal_composition_test.go:42-45`). An unexpected signal delivered to a test using `h.start`, followed by a flat/unrested observation, could exit the test process. No retained evidence establishes that sequence in the exploratory run.

Candidate containment, if this is separately taken up: have `seamHarness.start` use `serveWithShutdown` with an injected exit callback that records an unexpected authorized exit and cancels its context, so every composed test controls process termination. Keep the production `newShutdown` default and the signal composition test's explicit exit assertion. A regression should exercise the seam helper with a planned, flat drain. This is a test-harness hardening proposal, **not** a demonstrated production shutdown defect or a live-readiness fix.
