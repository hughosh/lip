### A3 attempt 1 — REJECTED (regression, not a gate failure)

Replaced the `*int64` / `*string` wire fields in `core/rig.go` with non-pointer
`optInt64` / `optString` types implementing `json.Unmarshaler`, aiming at
`reflect.unsafe_New` — 15.6% of allocations, one per non-nil pointer field, six
per delta frame.

Byte-identical rows, and worse on every metric:

    allocs/frame   39.20 -> 39.79
    total alloc    2,329 -> 3,467 MiB
    throughput     116,309 -> 100,159 f/s
    gc cycles      526 -> 634

The hypothesis was wrong in a way worth keeping. Implementing `json.Unmarshaler`
takes encoding/json OFF its fast path: instead of decoding straight into the
field, it materialises the raw bytes for that field and calls the method. That
costs more than the pointer allocation it removes. Pointer fields are not free,
but a custom unmarshaler is dearer.

Reverted. Recorded because "attack reflect.unsafe_New via custom unmarshalers"
looks obviously right from the profile and is not.

### A union decode is NOT available, and the reason is a rule

While looking for an alternative: decoding the envelope and the message in ONE
pass would remove the `json.RawMessage` copy (8.43% of allocations) and a whole
scanner pass. It is unsafe, and the ordering is why.

`Handle` decodes the envelope, runs the sequence-gap check, and only then decodes
the message. Python does a full `json.loads` and then the gap check. Those agree
today on both reachable cases: a malformed frame errors before the gap check in
both, and a well-formed frame with a bad field type reaches the gap check in
both. A union decode would break the second — the frame would fail before the
gap check, so `self.seq` would not be recorded and the NEXT frame would be
judged against a stale sequence number, fabricating or hiding a gap.

The two-stage decode is therefore load-bearing for P13's ordering, not an
artifact. Written up as P13a.
