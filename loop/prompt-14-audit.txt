### 2. The five tables

`hstore/schema.go`. `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`
applied on the single writable connection; a second connection is
`query_only=ON`; `user_version=1`, and a nonzero unknown version is REJECTED
rather than migrated.

Column and constraint notes:

- `owned_order.order_id` is nullable and UNIQUE, with
  `CHECK ((order_id IS NULL) = (bound_ms IS NULL))` — null or non-null together.
  The UNIQUE is also what lets `our_fill.order_id` reference it.
- `our_fill.order_id REFERENCES owned_order(order_id)`, so a fill can only be
  recorded against a durably BOUND order. That makes H-ORD-9 a foreign key
  rather than a convention.
- `state_event` CHECKs `scope IN ('global','market')`, `from_state <> to_state`
  and `"trigger" <> 'none'`. `trigger` is quoted; it is a SQLite keyword.
- `cfg.Params` is encoded with `encoding/json` straight off the struct. No
  `String()` anywhere near it.
- `our_fill` uses a literal `INSERT OR IGNORE`.
- `run`, `owned_order`, `state_event` and `anomaly` are insert-or-verify: a
  repeat with identical content succeeds, a repeat with different content is an
  error.
- Exact integer units throughout: `count_q` is quantity quanta, `price4` is
  ten-thousandths of a dollar, `fee_micros` is microdollars.
- The text journal is opened `O_APPEND|O_CREATE|O_WRONLY` and `Chmod(0600)`
  (chmod as well as mode, so an existing file created under a laxer umask is
  tightened), JSONL, one line per anomaly, carrying the anomaly id.

`TestSchemaIsExactlyThePilotFiveAndPragmasArePinned` enumerates `sqlite_schema`

### 3. Writer and health

Public surface is exactly your list plus `Pragmas()` — see FLAGGED CHOICES.
`Open` requires absolute paths, never deletes, never recreates.

- Unbounded lock-protected FIFO; capacity-one `Wake()` channel for results and a
  separate capacity-one channel to wake the writer. `submit` takes the mutex
  briefly and never waits for SQLite.
- The head is claimed WITHOUT holding the mutex across the write, which is the
  only reason `Health()` remains answerable while a write is in flight.
- A stalled or failed head stays queued. Nothing is ever evicted.
- Private backoff ladder `writerBackoff`, 50ms..5s, bounded delay and unbounded
  attempts.
- `Health` has a conservative zero value (not healthy, not adding) and read-only
  accessors. It exposes adding authority and diagnostics and has no mechanism
  that touches reducing or monitoring.
- Recovery: on failure, `recoverAt` is set to the sequence number of the last
  record then queued; health returns healthy only once `committed >= recoverAt`.

`RunHandle` and `DispatchPermit` have unexported fields only, invalid zero
values, no public constructors, and are issued ONLY through `Result`.
`DispatchPermit.Order()` re-checks that the carried order still names the coid
the reservation committed, then applies H-STORE-3: an adding permit requires
current healthy storage; a reducing permit does not.

### 4. Dual anomaly journal

`Store.applyAnomaly` is three resumable steps: row with `journaled_ms=NULL`,
then the appended-and-`Sync`ed JSONL line, then the `journaled_ms` update.
Progress flags live on the submission, so a retry after a failed journal append
resumes at the journal instead of re-inserting the row.

`Reader.PendingAnomalies` selects `journaled_ms IS NOT NULL AND delivered_ms IS
NULL`, ordered by `first_ms`, across every run.

`Store.reconcile` runs inside `Open`, before the store exists for anyone:

- every journal line must have a row, and the row must match it, or `Open`
  fails;
- a duplicated id with different content fails;
- a truncated final line (no terminating newline) or an unparseable line fails;
- a row with `journaled_ms` NULL whose id IS in the journal has step three
  completed using the journal line's own `written_ms`;
- a row with `journaled_ms` NULL whose id is NOT in the journal has its text
  appended and synced first, then step three.

On a journal or database failure the record stays in the queue (immutable, in
memory), health goes unhealthy, adding is revoked, the writer keeps retrying, and
monitor/state/fill records keep being ACCEPTED. The anomaly is not delivered
early because it never becomes delivery-visible.

The healthy->unhealthy transition emits an immediate `PushHealth` with
`Priority: urgent` whose body says persistence is unavailable and that ADDING is
revoked while reducing, monitoring and alerting continue. It carries no anomaly
ids at all, and the seal on that is asserted.

### 5. Durable ownership interface

`risk.OwnershipLookup` is now `OwnsOrders(orderIDs []string) ([]bool, error)`.
`hstore.Ownership` implements it from an index loaded exclusively from committed
`owned_order` bindings and updated only after commit. Three states per order id:
committed (ours), absent with nothing outstanding (foreign), submitted-not-
committed or failed (ERROR — never owned, never foreign).

`risk.Portfolio.ApplyFills` is now three passes:

1. collect unseen fills WITHOUT touching `seenTrade` (in-walk duplicates are
   deduplicated here too);
2. `OwnsOrders` over the whole batch. On error OR on a length mismatch: emit
   `SEV1 OWNERSHIP_LEDGER_UNAVAILABLE`, set `Stop`, set the new
   `FillEffects.Incomplete`, and return having mutated nothing;
3. only then mark seen and apply.

`wsx.applyFills` returns early on `Incomplete`, so `Applied[TruthFills]` stays
false and `noteTruth` is not called — the endpoint ages out and H-FAIL-4 stops
dispatch, which is the correct end state for a ledger outage.

`ForeignGuard.Classify` now returns `(ForeignEffects, error)`. The ledger is
consulted FIRST, for the whole walk, before any effect exists; an error returns
a zero `ForeignEffects` and the error. `Startup.attempt` turns that into a failed
pass that retries with backoff — not a set of foreign fills, and not a completed
reconciliation.

### 8. Ping package

Exactly your constructors. `LoadNTFYTopic` requires an absolute path and rejects

`[A-Za-z0-9_-]`, since the topic is a URL path segment.

`Topic` and `HTTPSDeadman` hold their value behind a `func() string` rather than

## FLAGGED CHOICES

Each of these is a decision your directive did not make. They are listed so you
can strike any of them.

1. **`risk.FillEvent` gained `ExchangeTsMs int64`.** `our_fill.exchange_ts_ms` is
   required and your `RecordFill` signature is fixed at
   `(RunHandle, risk.FillEvent, int64, bool)`, but `FillEvent` carried no
   timestamp. The field is populated from `rest.Fill.TsMillis` in both permitted
   converters. `RecordFill` rejects a zero.

2. **Permanent versus transient write failures.** Taken literally, "a failed head
   remains queued and is retried" wedges the queue forever on a constraint
   violation — a coid reserved twice with different content, a binding for a coid
   that was never reserved — and blocks every audit record behind it for the life
   of the process. So `SQLITE_CONSTRAINT` and this package's own rule violations
   are classified PERMANENT: popped, reported to the submitter through
   `Result.Err`, queue continues. Everything else (I/O error, SQLITE_BUSY, a full
   disk) is transient and retried indefinitely. A permanent failure does NOT flip
   store health — it is a caller error, not a persistence failure — but a failed
   BINDING marks its order id unclassifiable, so `OwnsOrders` errors for it and
   stays fail-closed.

3. **`Store.Health()` can mutate.** A write that never returns cannot be observed
   by the goroutine blocked inside it, so the writer-progress stall is detected
   by whoever asks for health. `Health()` takes the mutex and, past
   `defaultStallMs`, records the stall, revokes adding and sets the recovery
   watermark. The mutation is one-way: it can revoke adding and never grant it.

4. **`defaultStallMs = 5000`** — a private constant your directive does not name.

5. **Recovery watermark.** "healthy only after the failed record and prior backlog
   become durable" is implemented as: on failure `recoverAt` = the sequence of
   the last record queued at that moment; healthy again when `committed >=
   recoverAt`. Records submitted after the failure do not extend it.

6. **`Store.Pragmas()`** is on your list nowhere. It exists because `synchronous`
   and `foreign_keys` are per-connection, so `M-HS-PRAGMA` cannot be caught by
   asking the query-only reader.

7. **`DeliveryAttempt` carries a LIST of anomaly ids**, not one. "One aggregate
   push marks every represented row delivered" is only true if that update is
   atomic; per-row recording leaves a window in which a restart re-delivers the
   remainder.

8. **SEV3 rows are marked delivered by the heartbeat push that carried them.**

9. **The health notice is rendered from `Heartbeat` with an urgent title** and
   carries no anomaly ids.

10. **`ReserveOrder` rejects a coid that does not parse as ours** (`rest.IsOurs`).
    Not in your directive. The argument: §7.5's adoption classifies resting
    orders by that parse, so reserving an unparseable coid records an order the
    next incarnation will call foreign.

11. **`Reader` gained three fixed queries beyond the obvious**
    (`OwnedOrders`, `StateEvents`, `UndeliveredCount`) for the heartbeat and the
    schema tests. There is still no method taking SQL, and the seal test asserts
    that plus the absence of any `Query`/`Exec`/`Delete`-shaped exported method.

12. **The `ping` store-failure test breaks persistence by taking SQLite's single
    write lock from a second connection**, which produces `SQLITE_BUSY` — a
    transient failure — and recovers on rollback. No injected fake crosses the
    package boundary, but it is an unusual technique and worth your eye.

13. **`M-W-OWN`'s anchor was re-pointed** (see the red run above). It is one of
    the 72. Nothing was removed, renamed, or weakened, and its declared catching
    test is unchanged.
