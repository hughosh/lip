## FINDING 1

**SEVERITY** material
**CLAIM** Defeats claim 5 ("a restart reconciles the crash window in both directions"); collateral damage to claim 3's spirit and to availability (F18 becomes the only detector).
**MECHANISM** The anomaly JSONL append retry is not idempotent, and `Open` fails closed on the artifacts the retry itself creates. `applyAnomaly` re-stamps `sub.journalMs = s.nowMs()` on **every** attempt (writer.go:776). `fileJournal.appendLine` is write-then-sync on an O_APPEND fd with no offset tracking (sqlite.go:807-817). Three sequences, two of which need **no crash**:

- **(a)** `Write` succeeds, `Sync` returns a transient error (EIO/ENOSPC — exactly the failures the store advertises retrying forever, writer.go:29-31). The retry appends a second well-formed line: same `anomaly_id`, different `written_ms`. The current run continues happily. The **next** `Open` → `reconcile` → `dup && prev != l` → `permanent` (writer.go:297-303) → Open fails. The file never changes, so it fails **forever**.
- **(b)** `Write` returns a short-write error (ENOSPC mid-line). The partial bytes stay in the file; the retry appends a full line after them; the merged garbage line fails `json.Unmarshal` at the next Open (sqlite.go:852-856). Forever.
- **(c)** Power cut during the step-2 append → torn tail, no trailing newline → `parseJournal` refuses (sqlite.go:843-848). The reconcile doc (writer.go:277-287) enumerates deaths *between* steps 1/2 and 2/3 — not **during** step 2, the likeliest crash point in an anomaly burst.

**EVIDENCE** The suite is structurally blind to this: the fake journal injects failure **before** delegating to the real one (stub_test.go:297-302), so injected failures are atomic-nothing — a failure mode the real file does not have. `TestAnomalyIsInvisibleToDeliveryUntilBothJournalsAreDurable` proves "retry resumes at the journal" only under that unreal model; `TestAnomalyJournalIsPrivateAppendOnlyAndFailsClosed` enshrines torn-tail refusal as *intended*, framing it as tampering when it is also the store's own crash artifact. No `M-HS-*` mutation in `scripts/harness_negative_control.py` covers a post-write append failure — a catalogue hole. Concrete failing case: run `gatedStore`-style store against a journal whose `appendLine` writes the line then returns an error once; drain; reopen ⇒ `Open` returns "appears twice in the text journal with different content" permanently. Net effect: an unattended live-money harness that **cannot restart** after a routine transient disk error, until a human edits a file the system calls tamper-evident.

## FINDING 2

**SEVERITY** material
**CLAIM** Defeats claim 2 ("An in-flight or failed binding is an ERROR, never 'owned' and never 'foreign'") and produces exactly the H-ORD-9 catastrophe it forbids (false foreign → SEV1 → global stop) from the harness's own order.
**MECHANISM** The ownership model has a fourth state it cannot represent: **reservation committed (H-ORD-6 held), order dispatched, binding not yet committed**. `markPending` is keyed by `order_id`, which is unknowable before the ACK (ledger.go:111, 185-208); `loadBindings` loads only `order_id IS NOT NULL` rows (sqlite.go:645-647); so `OwnsOrders` answers `false` — FOREIGN, not error — for that order (ledger.go:61-82). - **Live:** between wire-out and the ACK being processed (stretched to seconds+ by a REST timeout while the post-only order rests and can be hit). The poller reads fills **first** each cycle (wsx/portfolio.go:151); `risk.ApplyFills` then marks the fill **seen**, excludes it from `our_fill` forever, raises `FOREIGN_FILL` SEV1 and requests global stop (risk/position.go:358-375). Unlike the pending-binding ERROR path — which degrades safely to `Incomplete` (wsx/portfolio.go:338-347) — `false` gives the caller no way to distinguish "mine, in flight" from "third party".
- **Crash before bind commit:** restart classifies through `ForeignGuard.Classify` (lifecycle/adopt.go:596; foreign.go:206-225) → `FOREIGN_FILL` SEV1 **plus a durable `foreign_fill` stop cause latched through `GlobalController.Decide`** — permanent WINDING_DOWN produced by our own fill. If the order fully filled during the gap it is absent from the resting walk, and `rest.Fill` carries no `ClientOrderID` (rest/read.go:407-418), so nothing the harness reads can ever repair it. Even for still-resting orders, the "same-coid recovery / adopted resting-order walk" named in `bindOrder`'s own doc (sqlite.go:431-433) **exists nowhere**: grep shows `BindOrder` is called only by tests.

**EVIDENCE** The spec says the ledger "covers every coid the harness has ever sent"; the classifier keys on `order_id`, so coverage is lost in exactly the crash window H-ORD-6 exists to survive. `TestDispatchPermitExistsOnlyAfterCommittedOwnership`'s comment (ledger_test.go:16-18) claims the durable coid prevents next-incarnation false-foreign — it doesn't; only a committed **binding** does. No test classifies a fill against a reserved-unbound coid (`TestOwnershipSurvivesRunsAndTerminalOrders` binds everything); no mutation covers it. Failing case: reserve+dispatch, crash pre-bind, restart, offer the fill → FOREIGN + durable latch + the fill never enters `our_fill` (corrupting lip-gp8's cash-flow evidence).
